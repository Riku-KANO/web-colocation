# 設計の概要

英語の詳細版は [docs/architecture.md](../architecture.md) です。

## 全体像

この設計の要点は、**ネットワークには部屋の「共有座標系」の値しか流さない**ことです。

- 各端末は自分の WebXR 参照空間 (local-floor) に対して、「ローカル ← 共有」の変換 M を持ちます。
- 共有コンテンツはすべて `sharedRoot` (行列 M) の子として置きます。
- 送信するときは、M⁻¹ で共有座標系に直してから送ります。

| 構成要素 | 担当 |
|---|---|
| クライアント (three.js + WebXR) | 部屋の描画、入力、キャリブレーション、音声 (WebRTC のメッシュ) |
| サーバー (Node.js、1 プロセス) | HTTP (`/api/config`、`/room-assets`、ヘルスチェック、メトリクス、静的配信) と WebSocket の同期 |
| `RoomRegistry` | 設定とテンプレートの解決、入室の可否、パスコード、主催者による設定変更、永続化、TURN のクレデンシャル |
| `Room` | 1 つの部屋の状態 (参加者・物・ストローク)。状態を変える唯一の場所 |

## 共有座標系とキャリブレーション

原点は部屋の anchor です。主テーブルの天板の中心、または床の上の点になります。

| モード | 入力 | 変換 M の決め方 |
|---|---|---|
| 仮置き | XR に入ったときの頭の姿勢 | 自分を自分の席に、席の向きで置く |
| 1 点 | 自分の机の中心をタッチ | 原点 = タッチした点。回転は「頭の方向」と「席の方向」から決める |
| 2 点 (同室) | 全員が同じ A, B をタッチ | 原点 = 中点、+X = A→B |

なぜ手動のキャリブレーションなのか:

- WebXR には標準の共有アンカーやクラウドアンカーがありません。
- そのため、どのブラウザでも動く手動キャリブレーションを採用しています。
- 合わせた後は、対応端末なら XRAnchor でトラッキングの補正に追従させます。

## 同期

**物 (所有権方式)**

1. 掴んだ瞬間、楽観的に自分の物として動かし始めます。
2. サーバーが先着順で所有者を確定します。
3. 負けた側はサーバーの姿勢に戻ります。

所有者以外の端末は、受け取った姿勢へ指数平滑化で滑らかに追従します。

**ホワイトボード**

- 座標はボード上の正規化座標 (u, v) で送ります。
- 点は 40 ms ごとにまとめて送ります。
- 1 本のストロークと 1 部屋の点数に上限があります。

**epoch**

主催者が部屋の設定を変えると、サーバーは次をまとめて行い、全員にスナップショットを送ります。

- 掴まれている物の解放
- 物を初期位置に戻す
- 無くなったボードのストロークを消す
- 席の割り当て直し
- epoch を 1 つ進める

古い epoch のまま届いた操作は捨てます。

**途中参加・再接続**

`welcome` で設定とスナップショットの全量を受け取り、状態を作り直します。

## セキュリティ

- すべてのメッセージを検証します (サイズ・件数・値の範囲)。
- WebSocket の Origin を検査します。
- SSO の識別ヘッダは、loopback で待ち受けているときだけ信頼します。
- パスコードは scrypt でハッシュ化し、試行回数を制限します。
- `/room-assets` はシンボリックリンクを解決したうえで、配信元フォルダの外を見せません。SVG は sandbox 化します。
- CSP は設定から自動で組み立てます。glTF には容量・三角形数・テクスチャ解像度の上限があります。
- TURN のクレデンシャルは短命で、入室者にだけ配ります。

## 規模

v0.2 は 1 プロセス・1 レプリカです。複数 Pod 化は Redis バックプレーン方式を予定しています ([roadmap](../roadmap.md))。
